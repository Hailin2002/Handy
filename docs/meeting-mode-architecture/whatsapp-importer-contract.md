## 2. Specialization points on the generic seam

The importer implements IC §3's `SourceIngestionPipeline` for
`ImporterKind::WhatsAppZipTxt` and owns stages 2–3 wholesale; stage 1 is
service + importer (container checks delegated), stages 4–5 are the shared
machinery and are **not** re-specified here. The specialization points are
exactly:

| Stage                  | What WhatsApp specializes                                                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inspect`              | delegates all accept/reject decisions to SEC rules; contributes only container-kind sniffing (§3.1) and the chat-file discovery report consumed by stage 2 (§3.2) |
| `preview`              | the entire §4–§7 behavior: variant lock, date-order resolution, line classification, outline construction, `VariantReport` + warning emission                     |
| `normalize`            | mechanical replay of the locked variant over the same bytes: `NormalizedItem`s per IC §6/§7 (keys `wa1-…`), `StagedMedia` with staging-relative paths             |
| `deduplicate`/`commit` | unchanged shared machinery; media enters per IC §8 with the §6 link-state matrix below                                                                            |

INV-1..INV-4 of IC apply unchanged: stages 1–4 write nothing, and `preview`
plus `normalize` are deterministic functions of (staged bytes, parser code,
`parser_version`, and the explicitly supplied `ImportOptions` of IF §9.3 —
see decision D-DISAMBIG in §4.4 for the one option that exists).

## 3. Container and chat-file detection

### 3.1 Container sniff (stage 1 contribution)

Applied to the staged bytes, before any decoding:

| Predicate | Condition                                              | `ContainerKind` | Next step                                                |
| --------- | ------------------------------------------------------ | --------------- | -------------------------------------------------------- |
| C-ZIP     | first 4 bytes = `PK\x03\x04`                           | `ZipArchive`    | SEC §2 phases A–C; then §3.2 discovery                   |
| C-TXT     | not C-ZIP; passes SEC §8 text rules (R-TXT-1..R-TXT-5) | `PlainText`     | decoded body is the transcript; skip §3.2                |
| C-OTHER   | anything else                                          | `Other`         | stage 2 fails `UnparsableFormat` (never sniffed further) |

Any SEC rejection (`E_*`) is terminal for the run at stage 1 (IC §3 failure
table; plan line 1466: no partial import). This importer adds **no** second
size/count/ratio limit anywhere — SEC §3's constants are the single source
of truth (decision D-LIMITS, §10).

### 3.2 Chat-file discovery inside a ZIP

After SEC acceptance, the staging tree holds sanitized files
(`S-STAGE-2`: `<index>_<sanitized-basename>` plus preserved safe relative
paths as metadata). Discovery runs over the **preserved relative paths**:

| Rule | Condition                                                                                   | Outcome                                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| F1   | exactly one member whose relative path is `_chat.txt` (case-sensitive, any directory depth) | that member is the transcript                                                                                                      |
| F2   | no `_chat.txt`; exactly one `*.txt` member in the whole archive                             | that member is the transcript (legacy/renamed exporters; covers SEC fixture `benign_cp437_legacy.zip`)                             |
| F3   | no `_chat.txt`; more than one `*.txt` member                                                | **ambiguous** → stage-2 failure `UnparsableFormat`, warning code `wa_chat_file_ambiguous` listing candidates — never a silent pick |
| F4   | zero `.txt` members                                                                         | stage-2 failure `UnparsableFormat` (`wa_no_transcript`)                                                                            |

All non-transcript members (media, sidecars, nested archives) form the
**staging member index**: the map `(relative path → staging file, declared
size)` used by §6. They are _not_ individually imported unless a message
links them (decision D-SIDECAR, §6.6); they remain preserved inside the
raw-original asset per §8.

## 4. Format-variant detection (gate G1)

### 4.1 Line pre-normalization

Before predicates run, each decoded line is normalized: strip Unicode
left-to-right/right-to-left marks (`U+200E`, `U+200F`) that Android exports
prefix to timestamps, NFC-normalize, strip the trailing `\r` of CRLF. The
normalized line feeds every predicate below; the _body_ carried into
`NormalizedItem.text` is the same normalized form (IC §6.2 rule 3).

### 4.2 Line predicates and variant table

Every known WhatsApp export line maps to exactly one class via the first
matching predicate, evaluated top-down:

| #   | Class               | Detection predicate (on the normalized line)                          | Normalization outcome                                                                                                                                                                                                                                                           |
| --- | ------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | Message (bracketed) | `^\[<datetime>\]\s` + rest — modern iOS/desktop bracket grammar       | item candidate; `occurred_at` from `<datetime>`; rest split into author/body per §5.3                                                                                                                                                                                           |
| P2  | Message (dash)      | `^<datetime>( - \| – \| — )` + rest — classic Android dash grammar    | item candidate; same split; en/em-dash separators accepted as one class                                                                                                                                                                                                         |
| P3  | Header              | matches neither P1 nor P2 **and** appears before the first P1/P2 line | never an item; recorded as display-name candidate for `ChatOutline.display_name` (extraction from header text is best-effort and locale-independent; an unrecognized header becomes display metadata plus warning `wa_header_unrecognized`/`HeaderUnrecognized`, never an item) |
| P4  | Continuation        | matches neither P1 nor P2 **and** appears after the first P1/P2 line  | appended to the current item's body per §5.2                                                                                                                                                                                                                                    |

`<datetime>` is the union grammar: `<date><sep><time>[ ]?[AM\|PM|am|pm]`
with date shapes `d.m.y(y)`, `d/m/y(y)`, `m/d/y(y)`, `y-m-d`, `y.m.d`,
`y/m/d` and time `h:mm[:ss]`. A timestamp token matches P1/P2 only if the
_whole_ datetime parses under exactly one date shape and one time shape;
partial matches are continuations (P4), never guessed timestamps.

File-level **grammar lock**: the importer records `grammar ∈
{bracketed, dash, mixed}` from which of P1/P2 matched. `mixed` is legal at
line granularity (each line is self-describing) and yields warning
`wa_mixed_grammar`, but changes no per-line behavior — there is no
file-level mode that could be chosen wrongly.

### 4.3 Date-order resolution (the one true ambiguity)

Date shapes `d/m/y` and `m/d/y` are lexically identical. Resolution is
evidence-based and deterministic:

| Rule | Condition                                                                                                                          | Verdict                                                                                                                            |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| D1a  | any timestamp's first component > 12 (and date shape is slash/dot two-component-first)                                             | `DayFirst` confirmed                                                                                                               |
| D1b  | else any timestamp's second component > 12                                                                                         | `MonthFirst` confirmed                                                                                                             |
| D1c  | else first component is 4 digits                                                                                                   | `YearFirst` confirmed                                                                                                              |
| D2   | evidence supports both orders in the **same file** (impossible for one genuine export; indicates corruption or concatenated files) | **preview-failure path**: stage 2 returns `UnparsableFormat`, warning `wa_date_order_conflict` — terminal, no option can repair it |
| D3   | every timestamp has all components ≤ 12 (genuinely ambiguous, e.g. all-US small-day export)                                        | **preview-failure path, recoverable**: see D-DISAMBIG below                                                                        |

**D-DISAMBIG (normative).** For D3, stage 2 returns `Err(UnparsableFormat)`
whose stable detail token is `wa:ambiguous-date-order`, together with a
`VariantReport.date_order_candidates = ["day_first","month_first"]` and up
to three sample lines in the warnings. The wizard surfaces the IF §9.2
failure state plus exactly one recovery action: re-run
`import_preview(runId, options)` with `options.date_order` explicitly set
(IF §9.3 already reserves the `options` parameter). The explicit choice is
pinned into the effective `parser_version` string (e.g.
`wa@1.0.0+order=day_first`), which keeps INV-3 determinism intact: same
bytes + same options ⇒ same batch. **There is no default guess**: an
unresolvable export never produces items, satisfying gate G1's „never
silent misparse“. A commit attempt while the ambiguity is unresolved is
unrepresentable — stage 4 requires a successful preview batch (IC §3).

Two-digit years use the fixed pivot `yy < 70 ⇒ 20yy, else 19yy` (WhatsApp
existed only after 2009; the pivot is a named constant of the parser, never
a device clock read — INV-3).

### 4.4 Zero-parse outcomes

If the transcript decodes but **zero** lines match P1/P2 (SEC fixture
`benign_chat_no_timestamps.txt` reaches here after a stage-1 ACCEPT):
stage 2 fails `EmptyImport` (IC §3). The validator-layer ACCEPT and the
importer-layer outcome are deliberately distinct layers — §9 maps this
fixture explicitly.

## 5. Timestamps, merging, system messages

### 5.1 occurred_at normalization (D-TZ)

Each matched `<datetime>` normalizes to ISO-8601 **UTC millisecond**
precision (IC §7.1): missing seconds become `:00`, missing milliseconds
`.000`. **Timezone decision D-TZ:** WhatsApp exports carry wall-clock times
with no offset. The importer interprets wall-clock **as UTC** (renders
`…T21:41:00.000Z` for `21:41` local), recording the assumption once per
source in `metadata` pair `("wa_local_time_assumed", "utc")`.

Rationale: converting via the importing device's zone would break INV-3
(same bytes imported from devices in different zones must yield identical
batches and keys) and shift keys between overlapping exports. Accepted
limitation (complexity budget): absolute instants may be off by the
exporter's zone offset; ordering within one chat is unaffected, and dedup
identity is unaffected because both exports of one chat share the wall
clock. Display-side re-localization is a presentation concern outside the
seam.

Minute-precision variants normalize to `:00.000`, mirroring IF §6.1 /
IC §7.1 — a second-precision export overlapping a minute-precision export
surfaces as `KeyConflict` (K1 consequence, already proven in IC §7.4).

### 5.2 Timestamp-continuation merging

Multiline messages (plan line 814: _„Er unterstützt mehrzeilige
Nachrichten“_) are rebuilt from P4 classes:

- **M1:** each P4 line appends to the current item's body, joined with a
  single `\n`, preserving internal blank lines; trailing whitespace is
  stripped once at body completion (IC canonicalization).
- **M2:** P4 lines before the first P1/P2 line cannot attach to any item;
  they are counted and emitted once as warning
  `wa_orphan_leading_lines { count }` (never silently dropped).
- **M3:** a merged body is capped at 64 KiB. Overflow truncates at the cap
  with warning `wa_continuation_truncated { item_sequence }` — explicit,
  deterministic, never silent.
- **M4:** media-marker extraction (§6.1) runs **after** merging, so a
  marker on its own continuation line links correctly.
- **M5:** `sequence` is the final merged-item ordinal in file order; it is
  presentation-only and never part of identity (IC §7 rule K1).

### 5.3 Author/body split and system messages

For a P1/P2 line, `rest` splits at the **first** `": "`:

- **S1:** the prefix is an author iff it is non-empty, ≤ 128 chars, and
  contains no line break (it cannot — lines were split first). Then
  `MessageRole::User`, `author_label = Some(prefix)`; the suffix is the
  body.
- **S2:** otherwise (`no ": "` in rest, or empty prefix) the line is a
  **system message**: `MessageRole::System`, `author_label = None`, whole
  `rest` is the body. Classification is structural, therefore
  locale-independent — encryption notices, join/leave, subject and
  push-name changes need no vocabulary table (decision D-SYSTEM; plan line
  814 _„Systemmeldungen“_ without a language allowlist).
- **S3:** "deleted message" tombstones are ordinary bodies under S1/S2.
  They are never interpreted as deletion instructions for other items —
  committed history is never retro-deleted (IF §6.3).

Group participants require no separate handling: labels flow into
`ChatOutline.participant_labels` as the distinct set of `author_label`
values (plan line 806: Teilnehmer), and into items as display labels only
(IC §6.2 rule 3 forbids JIDs/addresses surviving).

## 6. Media linking into the AssetStore (gate G2)

### 6.1 Marker extraction

A message references media iff its merged body contains a bracketed marker
token `<…>` (locale-dependent label text, e.g. `<Anhang: IMG-1234.jpg>` or
the bare omitted-placeholders) whose inner text ends in a known media
extension, or iff the exporter placed the attachment filename as the final
body token. The extracted **reference name** is the last path component of
the marker text. The marker stays in `text` verbatim (provenance), and the
link is recorded separately.

### 6.2 Link-state matrix (normative)

Resolution compares the reference name against the §3.2 staging member
index, in this order: (a) exact relative-path match, (b) unique basename
match. Exactly one of:

| Case                               | Detection                                                                                      | Behavior                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Linked**                         | exact relative path hit, or exactly one basename candidate                                     | `MediaRef { content_hash, mime_hint, size_bytes }` built from the staged file (hash computed during SEC's Phase-C stream, S-STAGE-3); `staging_relative_path` = the service-generated sanitized path; link row rides K4 (IC §8 rule 4)                                                                                             |
| **Missing**                        | no candidate in the index (plan line 815: _„fehlende Anhänge“_)                                | no `MediaRef`; body kept verbatim incl. marker; warning `wa_media_missing { item_sequence, name }`. Nothing fabricated, import continues                                                                                                                                                                                           |
| **Duplicate basename (unique)**    | ≥ 2 members share the basename but exactly one sits in the referenced `Media/`-style directory | treated as Linked via (a)/(b) with informational warning `wa_media_basename_match`                                                                                                                                                                                                                                                 |
| **Duplicate basename (ambiguous)** | ≥ 2 basename candidates with equal claim                                                       | **no link**, warning `wa_media_ambiguous { item_sequence, name, candidates }` — never a silent pick (mirrors gate G1's ambiguity doctrine)                                                                                                                                                                                         |
| **Oversized**                      | unreachable by construction                                                                    | SEC `MAX_FILE_UNCOMPRESSED` rejects the whole run at stage 1 before any member is extracted (SEC §5.1 R-LIMIT-2); the importer defines no second cap (D-LIMITS). Streaming guarantees: hashing during decompression stream, `put` via `PutSource::File` (AS §5.2) — no member is ever fully buffered in memory                     |
| **Path-traversal-named**           | unreachable by construction                                                                    | SEC §4 rejects the archive at stage 1 (`E_TRAVERSAL`/`E_ABSOLUTE_PATH`/…) before extraction; defense in depth, staging paths are service-generated (`S-STAGE-2`) and `StorageKey::parse` (AS §2.2) rejects any escaped key at `commit` (IC §10 point 3). Hostile names survive only as `assets.original_filename` display metadata |

Unsupported media (voice notes `.opus`, video, unknown MIME) follow IC §8
rule 7: stored like any asset, flagged unanalyzed, never dropped (plan
lines 1691–1692); voice-note transcription happens only via consented
post-commit jobs (plan lines 823–825) — never inside this importer.

### 6.3 No-duplicate-blobs and renumbering

Attachment filenames are renumbered per export (`IMG-…-WA0012.jpg` vs
`…-WA0047.jpg`); identity uses attachment **bytes** only (IC §7 K2), so
overlapping exports converge and blobs are stored only for NEW items
(IC §8 rule 5). Filenames persist solely as `assets.original_filename`
provenance.

### 6.4 Preview-time media inventory

`preview` populates `media: Vec<MediaOutline>` over the union of markers
found, each carrying its §6.2 link-state — the wizard's step-2 media count
(plan line 805: Medien) is therefore honest about missing/ambiguous
attachments **before** commit.

### 6.5 Binary access

Downstream consumption of stored media is exclusively
`AssetStore::get(key, ReadVerification::Full)` behind domain services;
frontends use the app's asset/serve channel (IC §8 rule 6, AS §2.1,
RB R5). Nothing in this contract introduces a second binary channel.

### 6.6 Sidecar decision D-SIDECAR

Members never referenced by any message (`.wa_metadata.json` sidecars,
nested archives, unreferenced media) are **not** individually put into the
AssetStore. They remain byte-preserved inside the retained original
archive (§8), reachable by re-inspection. Rationale: zero value lost
(original retained), N fewer blobs and link rows, no orphan-member
taxonomy to maintain. Complexity-budget decision, revisitable via a
`parser_version` minor bump.

## 7. Preview payload schema (gate G3)

### 7.1 Constraint

The payload returned by `import_preview(runId)` and rendered by wizard
step 2 (plan lines 805–806) must be expressible in the repo's existing
Tauri API contract mechanism: plain serde-serializable Rust types exposed
through tauri-specta, which generates the TypeScript definitions in
`src/bindings.ts` (verified: that file's header reads „generated by
tauri-specta“, and every existing command crosses the seam as
`Result<T, string>` over JSON values). Accordingly:

- every field is a JSON primitive, `Option`, `Vec`, or nested struct/enum
  of those — no binary payloads, no filesystem paths, no new transport
  format;
- the frontend receives the opaque `run_id` only (RB R5); staging paths
  never cross the seam (IF §9.3);
- the payload embeds the seam-owned `ImportPreview` aggregates (chats,
  media outlines, warnings, duplicate estimate, fast-no-op ref, IC §3)
  plus exactly one WhatsApp-specific extension, `VariantReport`, defined
  below.

### 7.2 Sketch

```rust
//! WhatsApp-specific preview payload sketch (std-only; compiles via
//! docs/meeting-mode-architecture/verify-sketch.ps1). At implementation
//! time each type additionally derives serde::Serialize and is registered
//! with tauri-specta, which emits the matching TypeScript into
//! src/bindings.ts — no hand-written mirror types.

/// Semver + optional explicit disambiguation suffix (§4.3 D-DISAMBIG),
/// e.g. "wa@1.0.0" or "wa@1.0.0+order=month_first".
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct ParserVersion(pub String);

/// Authoritative home: AS §3.2 — "sha256-<64 hex>".
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct ContentHash(pub String);

/// Explicit date-order resolution state (§4.3).
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum DateOrder {
    DayFirst,
    MonthFirst,
    YearFirst,
}

/// File-level grammar observation (§4.2); per-line behavior never depends
/// on this value.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum LineGrammar {
    Bracketed,
    Dash,
    Mixed,
}

/// Closed warning-code vocabulary owned by the parser version (§9 maps
/// fixtures onto these). Unknown codes are a parser bug, not a UI concern.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum WaWarningCode {
    ChatFileAmbiguous,
    NoTranscript,
    MixedGrammar,
    DateOrderConflict,
    OrphanLeadingLines,
    ContinuationTruncated,
    MediaMissing,
    MediaAmbiguous,
    MediaBasenameMatch,
    HeaderUnrecognized,
    NameDecodedCp437,
    InnerArchivesOpaque,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct WaParseWarning {
    pub code: WaWarningCode,
    /// Merged-item ordinal when the warning attaches to one item (§5.2 M5).
    pub item_sequence: Option<u64>,
    /// Detail parameters (names, counts); never raw user text bodies.
    pub detail: String,
}

/// How much of the file was understood — the honest-parse receipt shown
/// alongside the wizard summary (plan line 806).
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct LineStats {
    pub total_lines: u64,
    pub parsed_messages: u64,
    pub system_messages: u64,
    pub continuation_lines_merged: u64,
    pub header_lines_ignored: u64,
}

/// The single WhatsApp-specific extension to the seam's ImportPreview
/// (IC §3). Everything else reuses the seam types verbatim.
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct VariantReport {
    /// Which discovery rule found the transcript (F1..F4); "plain_text"
    /// for direct .txt uploads.
    pub chat_file_rule: String,
    pub grammar: LineGrammar,
    pub date_order_resolved: Option<DateOrder>,
    /// True iff the order came from an explicit user choice via
    /// ImportOptions (D-DISAMBIG), false when evidence-derived.
    pub date_order_explicit: bool,
    /// Present only on the D3 preview-failure path (with chats empty).
    pub date_order_candidates: Vec<DateOrder>,
    pub line_stats: LineStats,
}
```

### 7.3 Failure payloads are the same schema family

Preview failures cross the seam as the typed `IngestionError` discriminant
(IC §3) mapped to `IMP-E*` copy entries (IF §9.2); the D3 recoverable case
adds the `VariantReport.date_order_candidates` + sample-line warnings so
the wizard can render the choice. No failure path invents a second payload
format.

## 8. Original preservation (plan line 289)

Restating the binding norm because it is this importer's own promise
(machinery: IF §5, IC §8):

1. Stage-5 phase C1 puts the **byte-exact uploaded file** (`.zip` or
   `.txt`, whatever the user picked) as the source's raw asset under
   `assets/<fresh asst_id>/original.<ext>` (AS §2.2), hash-checked at AS
   verification point V1 against the stage-2 archive hash.
2. The `sources` row records `raw_asset_id` + `content_hash`; auditability
   fields answer plan lines 1470–1476 (which original file, which
   retention rule — the rule comes from `CommitDecision.retention_rule`,
   wizard step 3).
3. All extracted media and all unreferenced members (D-SIDECAR) remain
   reconstructible from that original; deleting the source follows the
   retention/delete flows of AS §8/§9 — this contract guarantees only that
   the raw asset exists and hash-verifies while the source row is live
   (`deleted_at` null).
4. No persisted record contains an absolute path (IC §8 rule 3); the
   serialization scan of IC §6.3 doubles as the check.

## 9. Mapping task-0040's fixtures onto stage behaviors

Source of truth for expected verdicts:
`tests/fixtures/import-security/manifest.json` (+ human-readable

## 10. Non-goals and complexity budget (gate G4)

Explicitly rejected, with reasons; additions require a documented
complexity-budget amendment:

1. **No connector/plugin framework.** Exactly two importers exist
   (`WhatsAppExportImporter`, `ManualFileImporter`); adding a third means
   writing another `SourceIngestionPipeline` impl, not building a registry,
   manifest format, or dynamic loading (IC §3 doc comment agrees).
2. **No new transport format.** Preview/progress/errors ride the existing
   tauri-specta JSON command/event channel (`src/bindings.ts` mechanism);
   §7 is a schema definition, not a wire protocol.
3. **No interactive format negotiation beyond one control.** The single
   date-order choice (D-DISAMBIG) is the entirety of user-facing format
   configuration; no per-message confirmation, no learning, no locale
   profiles.
4. **No timezone inference.** Wall-clock-as-UTC (D-TZ) is final for v1;
   per-export zone metadata would fork dedup keys.
5. **No recursive archive handling, no malware scanning, no encrypted-
   export prompts, no per-entry MIME allowlists** — all SEC non-goals
   (SEC §1.3), adopted by reference.
6. **No media transcoding, thumbnails, OCR, or analysis** in the importer;
   post-commit jobs own everything that touches model providers (IF §7.4,
   IC §9.5).
7. **No history rewriting:** tombstones, deletions and edits in newer
   exports never modify previously committed items (only additive `-rN`
   conflicts per IC §7 K3).
8. **No second size/cap constant set** (D-LIMITS) and **no second staging
   layout** (SEC §7.1 is the only one).
9. **No multi-chat archives:** one export = one chat; users with several
   chats import several files (each gets its own source row and preview).
   Chat-splitting heuristics are rejected as silent-guess territory
   (gate-G1 doctrine).

## 11. Verification hooks (maps to plan §14)

Tests this contract makes mandatory, in addition to IC §11 / IF §10:

1. **Variant lock determinism** — for each grammar fixture class, two
   `preview` runs produce equal `VariantReport`s (INV-3).
2. **Ambiguity doctrine** — an all-components-≤-12 export yields the D3
   failure with candidates, zero items, and succeeds identically after an
   explicit `options.date_order` re-run; a D2 conflict file yields the
   terminal failure regardless of options.
3. **Continuation merging** — multiline bodies, orphan leading lines and
   the 64 KiB cap each produce the specified warning codes and
   deterministic batches.
4. **System-message structural classification** — locale-varied system
   lines classify `MessageRole::System` without any vocabulary table.
5. **Link-state matrix** — one fixture-style case per §6.2 row asserts the
   linked/missing/ambiguous outcome, warning codes, and that ambiguous
   cases link nothing.
6. **Firewall interplay** — IC §6.3 scans pass with the assets'
   `original_filename` provenance column as the sole carrier of WhatsApp
   attachment names.
7. **Fixture-stage conformance** — the full §9 table asserted against
   `manifest.json` expectations (REJECT fixtures at stage 1 with mapped
   rule ids; ACCEPT fixtures at the listed stages).
