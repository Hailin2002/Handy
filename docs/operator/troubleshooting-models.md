## 1. Wie dieses Dokument zu lesen ist

Jede Zeile der Matrizen in Abschnitt 3 folgt dem Schema
**Symptom → Wahrscheinliche Ursache → Maßnahme → Zu sammelnde Evidenz**.
Jede Ursache ist eine Beschreibung _implementierten_ Verhaltens mit Codebeleg
(`datei.rs:Zeilen` bzw. Symbolname) gemäß Indexregel §1
(`docs/meeting-mode-documentation-index.md`, Abschnitt 1). Zeilennummern
beziehen sich auf den oben gepinnten HEAD-Commit.

Log-Evidenz sammeln: Anwendung mit `--debug` starten (CLI-Flag, siehe
`AGENTS.md`, Abschnitt „CLI Parameters“; Definition in
`src-tauri/src/cli.rs`), reproduzieren und die im Abschnitt „Evidenz“
genannten Zeilen aus dem Log auszuschneiden. Fehlgeschlagene Downloads werden
zusätzlich als Event `model-download-failed` gemeldet _und_ per `error!`
geloggt, damit der transiente Toast nicht die einzige Spur bleibt
(`commands/models.rs:51-58`, Kommentar zu #1579).

## 4. Diagnose-Schnellpfad (Reihenfolge)

1. `--debug`-Log einschalten (CLI-Flag `--debug`, `AGENTS.md`, Abschnitt
   „CLI Parameters“) und Fehlversuch reproduzieren.
2. `error!`-Zeile „Model download failed for …“ lokalisieren
   (`commands/models.rs:54`) — ihr Text ordnet den Fall direkt einer Zeile
   aus Abschnitt 3 zu (stalled → R3, verification → R7, incomplete → R8,
   mirror → R4, extract → R10).
3. Ablageorte gegen Abschnitt 2 prüfen: liegt schon eine vollständige Datei
   im Models-Dir bzw. HF-Cache (R12/R13)? Portable Installation?
4. Bei Netzverdacht: geloggte HF-/Mirror-URL direkt testen (R4); bei
   wiederholtem Prüfsummenfehler Mittelmann (Proxy/Virenscanner) prüfen (R7).
5. Nach jeder Maßnahme: erneuter Downloadversuch und Vergleich der
   „attempt {n}/4“-Logzeilen (`downloads.rs:84-90`) mit dem Fehlerlauf.
